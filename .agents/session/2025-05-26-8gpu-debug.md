## 执行内容
- 在 debug pod 上下载 Qwen-Image-Edit-2511 并 tar 到 S3（33 GB）
- 发现 `--fast` 模式仍需 6-8 min 重新编译 CUDA 扩展（根因：tar 只保存源码，`uv pip install` 每次 rebuild wheel）
- 新方案：**直接打包编译好的 site-packages（含 .so）到 S3**，恢复时只需 tar 解压（~3s）
- 修复 nvdiffrast `_nvdiffrast_c.so` 遗漏问题（JIT 编译产物在 site-packages 根目录）
- 更新 setup 脚本：优先用 `flow_grpo_cuda_site_packages.tar`（预编译），fallback 到旧 `flow_grpo_cuda_ext.tar`（需 rebuild）
- `--fast` 总时间从 10 min 降至 **3 min 12 秒**
- 提交 8 卡训练 `ericzyma-job-normal-20260526-130815`：**setup 成功，训练启动 + wandb 连接后 fail**

## 调试经验
- **site-packages tar 必须包含顶层 .so 文件**：`_nvdiffrast_c.cpython-312-x86_64-linux-gnu.so` 在 site-packages 根目录而非 nvdiffrast/ 子目录内
- **S3 FUSE mkdir -p 可以创建目录**：tar 写入前必须确保目录存在
- **flash-attn 4.83s "编译"实际是从 uv cache 恢复 wheel**：Python 3.12 + torch 2.6.0 组合有缓存命中

## 当前问题
8 卡 normal 训练在 setup 完成、训练正常初始化（4 rank DDP + wandb）后约 1 分钟内 fail。

### 可能原因
1. **多卡 OOM**：4 rank 同时加载 Trellis2-4B (~4B params * 4 GPU) + 4 张 Guidance GPU 加载 Qwen
2. **多卡版本的代码 bug**：单卡共享模式验证通过，但 4+4 分离模式可能有不同代码路径
3. **集群 scheduler 杀进程**：启动阶段内存峰值过高被 OOM killer 终止

### 排查建议
1. 检查 wandb run `z3lmibfz` 是否有 crash log
2. 开 debug pod（至少 2 卡）验证 2+2 模式
3. 考虑减少并行度：2 rank 训练 + 2 Guidance（4 卡即可）
